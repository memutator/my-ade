## Findings

**1. [implementation] mahasd caches one execution-host session and every recovery/lifecycle host call closes it**

- Location: `packages/mahas-runtime/src/composition.ts:97-120,213-225,282-318`; `packages/mahas-runtime/src/lifecycle/reconcile.ts:192-284`; `packages/mahas-runtime/src/recovery/identity-probe.ts:237-264`; `packages/mahas-runtime/src/recovery/stop.ts:299-356`; `packages/mahas-runtime/src/recovery/reconciler.ts:155-185,204-235`.
- Contract: REQ-12 / C-HOST transport — mahasd must keep a fenced session to the host that owns the processes; S-LIFECYCLE §5 ensure-service connects to the live host rather than dropping it.
- Evidence: `composeRuntime` stores a single `HostSession` and `hostClient`/`hostClientByEndpoint` return `fenced(existing)` with no liveness check (`composition.ts:282-284,307-309`). Recovery and startup reconcile all call `client.close()` in `finally` after probe/stop/inventory/hello. `fenced.close` closes the underlying socket (`composition.ts:119`) but the map entry remains, so the next `host.process.spawn`/`worker.stop` reuses a dead client (`HostCallError CONTROL_UNAVAILABLE`, `hostClient.ts:94-95,141-144`). Startup reconcile is especially sharp: `probeHost` issues a second `host.hello` *without* the endpoint-file token (`reconcile.ts:197-209`) on the already-authenticated session; `host.hello` always requires `credential.token` (`host.ts:511-516`), so hello fails, then `finally` still closes the session that `attachHost` just acquired.
- Consequence: after a successful compose attach, the first `runtime.reconcile` (including boot `startupReconcile`, `main.ts:435`) severs host control. Subsequent managed spawn/stop/input fail until mahasd is restarted — and a restart hits the same close. Reattach/stop/drain cannot reach the OS process they claim to own.
- Requested correction: recovery/lifecycle must not close the composition-owned session (use a dedicated dial, or a borrow that does not `close`). Drop closed sessions from the map and re-`attachHost`. Pass the endpoint-file token (or skip hello) on an already-authenticated connection.
- Target: IMP-23 (startup reconcile + composition session) with IMP-22 (probe/stop/inventory `close`).

**2. [implementation] C-HOST request/response shapes are not the ones mahasd reads — probe/stop cannot name a process, and confirmed host receipts collapse to unknown**

- Location: host input `packages/mahas-execution-host/src/process-manager.ts:616-625,327-347,414-428,508-557`; mahasd callers `packages/mahas-runtime/src/recovery/identity-probe.ts:229-236,267-277`; `packages/mahas-runtime/src/recovery/stop.ts:308-341`; `packages/mahas-runtime/src/launch/start-coordinator.ts:1035-1058`; `packages/mahas-runtime/src/lifecycle/reconcile.ts:257-266,505-531`.
- Contract: C-HOST `host.process.probe`/`stop`/`spawn`/`effect.get`; S-LIFECYCLE §3 — confirmed OS reject is exited+rejected; lost confirmation is unknown, never the reverse.
- Evidence: (a) Host `expectedIncarnation` reads `payload.processIncarnation` or top-level `spawnNonce`/`pid`. Recovery sends `expectedProcessIncarnation` only (`identity-probe.ts:229-236`, `stop.ts:308-312`). Probe therefore looks up `procs.get('')` and returns `liveness:'unverifiable'` / `no-host-record` (`process-manager.ts:435-440`); stop throws `PROCESS_UNVERIFIABLE` (`process-manager.ts:473-474`). `worker.resume` reattach and `worker.stop` cannot address the live child. (b) Host stop returns `{stop: StopReceipt}` with `receipt.outcome === 'exited'` (`process-manager.ts:547-558`); `callHostStop` reads `res.outcome ?? res.result ?? res.state` (`stop.ts:323`) — all undefined — so a confirmed SIGKILL is recorded `stop_unknown` (`stop.ts:336-341,449-476`). (c) Host spawn reject is `{processIncarnation:null, spawn:{state:'rejected', errno}}` (`process-manager.ts:327-347`); coordinator checks `out.state === 'rejected'` then `!identity` → `START_UNKNOWN` (`start-coordinator.ts:1043-1058`), violating S-LIFECYCLE “명백한 OS reject면 exited+start rejected”. (d) `host.effect.get` returns `{found, effect:{state,...}}` (`host.ts:672-688`); both reconcilers read `receipt.state` at the wrapper (`lifecycle/reconcile.ts:264-266`) so a confirmed spawn/stop receipt is treated as non-conclusive and rewritten `unknown`.
- Consequence: the process/stop cut-points the review is charged to check cannot settle on positive evidence. A successful host stop leaves the execution `stop_unknown` with claims held; a definite `ENOENT` spawn is `start_unknown`; reattach never sees `liveness:'live'`. Ambiguous boundaries are not merely preserved — confirmed outcomes are collapsed *into* unknown.
- Requested correction: agree one wire shape (host field names `processIncarnation` / nested `spawn`/`stop`/`effect`, or mahasd adapters that unwrap them). OS `rejected` must map to a failed stage + `exited`, not `START_UNKNOWN`. `effect.get` must read `effect.state`.
- Target: IMP-22 (probe/stop/effect adopt) with IMP-18 (optional host alias for `expectedProcessIncarnation`) and IMP-19 (spawn reject).

**3. [implementation] Boot `runtime.reconcile` is not `reconcileExecutions`; if inventory were obtained, pid presence would be treated as live without birth proof**

- Location: wired path `packages/mahas-runtime/src/lifecycle/operations.ts:74-96` → `lifecycle.ts:149-166` → `lifecycle/reconcile.ts:325-384,421-434`; unused path `packages/mahas-runtime/src/recovery/reconciler.ts:269-275` (`reconcileExecutions` is only re-exported from `recovery/index.ts:41`, never registered or called); takeover payload `lifecycle/reconcile.ts:424-432`.
- Contract: C-RECOVERY restart algorithm steps 3–4 — lease only with dead/handoff proof; match by effectKey·spawnNonce·process birth; unmatched orphan quarantine; inventory is not liveness. D-EXEC §3 / REQ-11 / REQ-15.
- Evidence: IMP-22’s reconciler probes via `host.process.probe`, classifies with `compareProcessIncarnation`, and quarantines orphans (`reconciler.ts:437-494`, `orphan.ts:271-288`). IMP-23’s `runtime.reconcile` never calls it. The wired `judgeExecution` treats `entry.state === 'running' || entry.pid != null` as reattach and writes `liveness:'live'`, claiming “process birth matches” without comparing `birthEvidence` (`lifecycle/reconcile.ts:374-383`). Host `host.inventory` itself labels every stored row `liveness:'unverifiable'` / `probed:false` (`host.ts:598-601`). Takeover proof is `{priorRuntimeInstance:'superseded-by-epoch',...}` which is not `kind:'dead-evidence'|'explicit-handoff'` (`lease.ts:311-314`); the host falls back to its own probe (safe) but the control plane does not supply the specified proof. Combined with Finding 1, the pass currently fails hello and records `left-unknown` — the pid-as-live branch is latent until hello is fixed, then it would promote unverifiable inventory to live.
- Consequence: boot reconciliation does not reattach by spawnNonce+birth, does not quarantine orphans, and is one hello-fix away from marking a reused or host-restarted pid `live` without `host.process.probe`. Writer claims stay, but control pointers would lie.
- Requested correction: `runtime.reconcile` / `startupReconcile` must run `reconcileExecutions` (probe + identity compare + orphan quarantine). Inventory pid/state must not be live evidence. Takeover proof must be `dead-evidence` or `explicit-handoff`.
- Target: IMP-23 (wire) with IMP-22 (the unused engine).

**4. [implementation] `worker.release` is implemented and listed but never registered**

- Location: `packages/mahas-runtime/src/recovery/index.ts:8-38`; `packages/mahas-runtime/src/recovery/reconciler.ts:903-1118` (`makeReleaseHandler`); `packages/mahas-runtime/src/api/registry.ts:143`; `packages/mahas-runtime/src/composition.ts:419-428`.
- Contract: C-LAUNCH `worker.release`; IMP-22 instruction §4.5 / §6; REQ-16 — release/retain/transfer is the explicit leftover-resource operation, distinct from Task settlement and from `worker.stop`.
- Evidence: `registerRecoveryOps` registers only `worker.stop` and `worker.resume`. The header states worker.release is “deliberately left unregistered”. `makeReleaseHandler` exists and correctly refuses release without exit/quiescence (`reconciler.ts:1090-1103`) and routes retain/transfer/release to `claim.*`. Grep shows no `register(..., worker.release)`. Admission therefore yields `UNAVAILABLE_OPERATION`. `worker.stop` nextAllowedActions still name `worker.release` (`stop.ts:403,445,462`).
- Consequence: after a confirmed stop, leftover worktrees/claims cannot be released through the declared op. Dirty/unknown resource handoff (review directive 5) is a dead surface; operators are pointed at an op that does not exist.
- Requested correction: register `makeReleaseHandler` on the recovery registry (it needs the `OperationRegistry` already in `RecoveryDeps.makeCaller`), or remove it from OPERATION_TABLE and member grant vocabulary until then.
- Target: IMP-22.

**5. [implementation] `runtime.shutdown` drain-and-stop never issues `worker.stop`**

- Location: `packages/mahas-runtime/src/main.ts:274-278,299-309`; `packages/mahas-runtime/src/lifecycle/shutdown.ts:141-152,221-229`; `packages/mahas-runtime/src/lifecycle/lifecycle.ts:334-342`.
- Contract: C-RECOVERY `runtime.shutdown` drain-and-stop; S-LIFECYCLE §6 — 신규 배정 중지 → worker stop intents → 확인/unknown 기록 → 필요 자원 유지 → DB close.
- Evidence: `MahasdLifecycle` is constructed with `caller: opts.caller ?? null` *before* `composeRuntime`. Nothing later assigns the composed `makeCaller` onto `lifecycle.deps.caller`. `issueStopIntent` returns `stop-not-attempted` when `caller` is null (`shutdown.ts:147-152`). Drain still marks the stop-intents *stage* completed (`shutdown.ts:263-270`) with residuals, so the receipt looks like a finished drain that did not signal any process. `leave-executions` is honest (no stops). Timeout residuals are preserved (aligned) — but the stop intents themselves are never attempted.
- Consequence: operator drain-and-stop leaves executions running. The shutdown record can read `completed` while processes and write claims remain live. Combined with Finding 1/2, even a wired caller could not currently confirm host stop.
- Requested correction: inject `composeRuntime`’s caller into `MahasdLifecycle` after composition; drain must call `worker.stop` with exact generation/incarnation and record confirmed vs unknown per execution.
- Target: IMP-23.

**6. [implementation] native-resume / fresh admit a new generation that `worker.start` cannot spawn**

- Location: `packages/mahas-runtime/src/recovery/resume.ts:410-462,469-520`; `packages/mahas-runtime/src/launch/start-coordinator.ts:207-208,433-444`.
- Contract: C-LAUNCH `worker.resume` — “native/fresh는 별도 start intent와 신규 credential”; C-RECOVERY table — native-resume creates a new process and execution generation; fresh creates a new conversation/bundle/credential/execution. REQ-15 — a new process resume increments generation.
- Evidence: The three kinds are separate functions (aligned). native-resume probes the old process, fences inbox, revokes old credentials, bumps `members.generation`, and returns `nextAllowedActions: ['worker.start']` on the *same* `launchPlanId` (`resume.ts:440-462`) without inserting a new execution or launch plan. `worker.start` returns immediately if the plan receipt is already `terminal` (`start-coordinator.ts:207-208`) and `stageAdmitted` rebinds to the existing `executions` row for that `launch_plan_id` (`start-coordinator.ts:433-444`) without creating generation+1. fresh similarly does not stop or replace the old execution (`resume.ts:469-520`). There is no other start-intent factory.
- Consequence: native-resume/fresh are admission receipts that cannot produce a new process. The only working resume kind is reattach, and reattach is blocked by Finding 2. Changed-role “new conversation” cannot be started through the declared path.
- Requested correction: native-resume/fresh must create a new LaunchPlan (or a new start receipt keyed by generation) and a new execution row; `worker.start` must not treat a used plan as the new generation’s spawn. Old process must stay fenced (native-resume already requires dead/quiescent).
- Target: IMP-22 (resume admission) with IMP-19 (`worker.start` generation).

**7. [implementation] stdin initial-attachment evidence is recorded without writing bytes to the process**

- Location: `packages/mahas-runtime/src/launch/start-coordinator.ts:1005-1014`; `packages/mahas-runtime/src/launch/initial-attachment.ts:349-376`; `packages/mahas-execution-host/src/pty-manager.ts:26-27,170-176,261-267`; `packages/mahas-execution-host/src/process-manager.ts:270-274`.
- Contract: C-LAUNCH input stages — `initial_attached` means the verified recipe connected bytes to argv/stdin; S-LIFECYCLE §3 “initial input 후 응답 전” unknown injection must not be reported as attached; C-HOST ProcessSpec `initialStdin?: ContentRef`.
- Evidence: `buildSpawnSpec` returns `stdinBytes` beside `spec` and does not set `spec.initialStdin` (`initial-attachment.ts:360-376`). Coordinator puts `{digest, bytesB64}` on `spawnPayload.initialStdin`, a sibling of `spec` (`start-coordinator.ts:1005-1014`). Host spawn only reads `payload.spec` as `SpawnSpec` (`process-manager.ts:270`) and writes `spec.initialStdin` as a string (`pty-manager.ts:170-176`). The b64 object is ignored. `stageInitialAttached` then treats `byteDigest` on the local evidence as attached (`start-coordinator.ts:1138-1178`).
- Consequence: a stdin-route harness is marked `initial_attached` / `awaiting_join` with no bytes on the child’s stdin. The initial-input cut-point is closed as success without an injection receipt that the process observed. Duplicate prompt on retry is correctly refused (`start-coordinator.ts:217-229`) — the first prompt simply never ran.
- Requested correction: put stdin bytes on `ProcessSpec.initialStdin` (host-decoded) or have the host read `payload.initialStdin.bytesB64`. Do not confirm `initial_attached` from planner evidence alone.
- Target: IMP-19 (with IMP-18 stdin decode if the ContentRef object is the intended wire).

**8. [implementation] workspace mutations refuse the live controller when the advisory lease TTL elapses, and mahasd never renews**

- Location: `packages/mahas-runtime/src/composition.ts:213-217` (`ttlMs: 120_000`); `packages/mahas-execution-host/src/workspaces/common.ts:107-125`; `packages/mahas-execution-host/src/lease.ts:87-88,352-377`; `packages/mahas-execution-host/src/main.ts:112-127` (`verifyLease` default true).
- Contract: D-EXEC §3 / C-HOST `host.acquire` — “TTL alone 금지”; expiry is not death and must not move the writer. Mutation fencing is epoch+leaseProof (`S-LIFECYCLE §2`).
- Evidence: `requireLeaseProof` (process spawn/stop) does not consult `expires_at`. Workspace `assertLease` fails `SCOPE_DENIED` when `expires_at <= now` even if epoch and the live controller identity still match (`workspaces/common.ts:114-119`). Compose acquires once with a 120s TTL and never re-acquires. After two minutes, `host.workspace.prepare`/`release` fail while `host.process.spawn` still passes the same fence token.
- Consequence: a live mahasd loses workspace claim/cleanup while still able to spawn into a checkout it can no longer prepare or release. This is not TTL-takeover of an old writer (that path is correctly refused in `lease.ts`), but TTL still disables the *current* writer on the resource primitive — leftover-resource cleanup (directive 5) times out into a false “not authorized”.
- Requested correction: either stop using `expires_at` as a workspace mutation fence (epoch+fence token only, matching process ops), or have mahasd renew the same-owner lease before expiry. Expiry must not be death and must not brick the holder.
- Target: IMP-17 (lease fence consistency) with IMP-16 (workspace `assertLease`) / IMP-23 (renewal).

**9. [implementation] `backup.restore` marks liveness unverifiable but leaves generation, credentials, and execution state able to act as a live writer**

- Location: `packages/mahas-runtime/src/operations/restore.ts:253-278,359-368`.
- Contract: C-RECOVERY `backup.restore` — “모든 과거 실행은 reconciliation 필요로 시작”; “restore가 과거 PID 권한 부활시키지 않음”; REQ-15/27.
- Evidence: `markExecutionsUnconfirmed` is `UPDATE executions SET liveness='unverifiable' WHERE liveness='live'` only (`restore.ts:359-364`). `state` (e.g. `ready`), `generation`, `execution_credentials.revoked_at`, and `resource_claims` are untouched. A restored worker credential can still `execution.join`/`task.accept` against a generation whose process identity is a copied pid. Restore does not bump generation or require `runtime.reconcile` before writable use of those rows (writable readiness is the next mahasd boot’s reconcile, which is Finding 3).
- Consequence: restoring a backup can present old executions as joinable/writable members without host/process incarnation proof. That is the PID-authority resurrection the contract forbids, even though the liveness column is no longer `live`.
- Requested correction: on restore, revoke live execution credentials, keep or move state to a reconciliation-needed value that join/start refuse, and leave claims held-unknown until explicit `worker.release`/`runtime.reconcile`. Do not leave `ready`+valid bootstrap/full credentials.
- Target: IMP-29.

## Limitations

- Static review only — no daemon boot, no kill/crash injection, no harness spawn. Findings 1–3 and 5–7 are code-path reasoning (wire field names, `close()` on a shared session, null caller), not observed runtime failures. Live crash/kill belongs to VER-06..08.
- Packaged-app daemon lifetime was verified as **dev-only**: `ensureControlPlane` returns immediately when `app.isPackaged` (`src/main/runtimeClient.ts:125-140`). Installed mahas reports `CONTROL_UNAVAILABLE` until an operator starts mahasd/execution-host. Dev spawn uses `/dev/zero` so execution-host stdin EOF does not kill the daemon (`runtimeClient.ts:133-161`; host still exits on stdin end, `execution-host/src/main.ts:144-146`).
- Host-side `verifyInputLease` is never wired (`process-manager.ts` `ProcessOpsDeps.verifyInputLease` unused; `terminal-stream.ts:842-843` then returns `leaseVerified:false` but still writes). Enforcement reviewed here is the mahasd `terminal.input`/`resize` CAS (`client/store.ts`). Direct same-uid socket calls to the host bypass InputLease; v1 same-uid trust is assumed, not re-tested.
- `reconcileExecutions` / `drainEffectOutbox` / `makeReleaseHandler` were read as the IMP-22 design; they are not on the boot path (Finding 3/4). Their remaining internal envelope bugs would matter only after they are wired.
- Unmanaged desktop `pty:*` sessions are out of this review except the documented split: they remain app-owned and die with the UI (`runtimeClient.ts:8-9,223-226`).
